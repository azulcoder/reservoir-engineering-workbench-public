# Bridge: manual comparison of case B1 against an external well-test package

## Status

**SAPHIR MANUAL COMPARISON — NOT RUN.**

No comparison against Saphir, or against any other commercial or third-party well-test
package, has been performed for case B1 or for anything else in this repository. This
document is a procedure, not a result. Nothing here is evidence, and no claim anywhere in
this project may cite it as evidence.

The status line above is the only place the status is recorded. If the comparison is ever
run, this document is updated in place with the outcome — including an unfavourable one —
and the case report's limitations section is updated with it.

## Why this document exists

Every number in case B1 is self-generated end to end. The data come from a line-source
solution this project implemented, the interpretation comes from code this project wrote,
and the checks come from oracles this project selected. The independence B1 achieves is
between the *forward and inverse methods*, which is real but limited: it cannot catch an
error in a convention shared by both, and the case report says so in its limitations.

An interpretation of the same data by software built independently of this project, by
people who never saw this code, would test exactly that shared-convention layer. It is the
cheapest available increase in independence and it is the reason this procedure is written
down rather than left as an intention.

## What would be compared

Input: `docs/bridges/b1_pressure_history.csv`, generated by `scripts/export_b1_bridge.py`
from the audited run snapshot. It carries 85 points of elapsed time and pressure over the
declared interpretation window, together with the well and fluid properties needed to
interpret them. It does not recompute anything; the exported numbers are the numbers the
case reports.

deliberately. Blinding the operator would be better practice, and the header should be
stripped before handing the file over if the comparison is run under blinded conditions.

## What agreement would and would not establish

No agreement threshold is declared here in advance, and that is deliberate: the right
threshold depends on the package's own numerics, its default derivative smoothing, and
whether it fits the window this case declares or chooses its own. Declaring a number now
would be choosing a threshold without understanding what it is a threshold on. The
threshold must be fixed and written into this document *before* the external run is
executed, in the same way B1's own criteria were fixed before B1 ran.

What agreement would establish: that the field-unit conventions `141.2` and `0.0002637`,
the `ln4 - gamma` grouping, and the skin sign convention as implemented here match those of
an independent implementation. These are the quantities B1 explicitly does not verify — the
evidence card records them as taken as given.

What agreement would **not** establish: anything about real reservoirs, about wellbore
storage, about gas wells, or about whether the model is appropriate for any actual well.
Both implementations would still be solving the same idealised problem. A commercial
package agreeing with this one is not field validation and must never be reported as such.

What disagreement would establish: depending on where it fell, either a defect here or a
difference in convention. A disagreement in `kh` with agreement in the semilog slope would
localise the problem to the unit constants. A disagreement in skin with agreement in `kh`
would point at the skin convention or the reference time. Either outcome is a useful result
and would be reported, not discarded.

## Procedure, if it is run

1. Record the package name, version and platform, and the operator, in the table below.
2. Fix and write down the agreement threshold for each quantity, before importing anything.
3. Decide and record whether the comparison is blinded; if so, strip the header comments
   that disclose `k` and `s`.
4. Import `b1_pressure_history.csv` as a constant-rate drawdown at 350 STB/D with the well
   and fluid properties in its header.
5. Interpret it however the package's own workflow directs. Do not force it to use this
   project's window; if the package chooses a different window, record which, because
   section 4 of the case report quantifies exactly what that choice costs.
6. Record the recovered `kh`, `k`, `s`, slope and derivative plateau.
7. Update the status line at the top of this document and the comparison table, whatever
   the outcome. Update `cases/B1_iarf_known_answer/report.md` limitations to match.
